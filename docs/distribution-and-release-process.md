# Distribution, onboarding skills, and the release cycle

*Proposal, 2026-10-01; decisions and what was implemented are in §5.*

PyCLM is about to have its first release since the core refactor (63
commits past `v1.0.1`). This note proposes three things: how a newcomer
gets PyCLM and a first run, a set of agent skills that carry a newcomer
from an idea to a run, and how two researchers and an agent should
develop and release from here on.

## 1. Where things stand

- **Not on PyPI.** `https://pypi.org/pypi/pyclm/json` returns 404, so
  the name is free. `.github/workflows/publish.yml` exists (trusted
  publishing on a GitHub release) but has never published. The only way
  in is `git clone` + `uv sync`.
- **The version is wrong.** `pyproject.toml` says `0.1.0`; the tags say
  `v1.0.0`, `v1.0.1`. Nothing ties the two together.
- **CI tests on Ubuntu only**, Python 3.11, with the locked interface-71
  stack. The scope runs Windows, and pip users get the newest pymmcore,
  so neither the scope's platform nor the open ranges are tested.
- **Every install gets the scope stack.** The core dependencies include
  napari + PySide6 (viewer), `notebook`, `pandas-stubs` (a typing
  package at runtime), and `toml` (the stdlib `tomllib` reads TOML on
  3.11+). Someone who only wants to read a `.zarr` on a laptop still
  installs Qt and Jupyter.
- **Global console scripts named `gui` and `convert_hdf5s`.** `gui` will
  collide with something on a user's PATH; both are now `pyclm gui` /
  `pyclm export`.
- **Custom methods need Python.** `pyclm run`/`check`/`preview` see only
  built-in methods; a researcher's own `PatternMethod` runs only through
  `run_pyclm(pattern_methods=...)`. Writing their own method is what
  most people incorporating PyCLM into research end up doing, and that
  path is currently the least supported.
- **No zero-hardware first run.** A dry run needs TIFs the newcomer does
  not have.

## 2. Distribution changes, in priority order

1. **Publish to PyPI as `pyclm`, version `2.0.0`.** This release breaks
   the TOML schema, storage format, and developer API, so it is a major
   version. Configure the trusted publisher on PyPI (project `pyclm`,
   repo `Harrison-Oatman/PyCLM`, workflow `publish.yml`, environment
   `pypi`); do a first upload to TestPyPI. Then
   `pip install pyclm` / `uv tool install pyclm` works.
2. **One version source.** Either keep `version` static in
   `pyproject.toml` and make the release checklist bump it (simplest;
   `uv version --bump minor`), or derive it from the git tag. I
   recommend static plus a CI step that fails a release whose tag does
   not equal `pyproject` `version`.
3. **Split the dependencies by who installs.**
   - core: what `check`, `preview --image`, dry runs, and `pyclm.io`
     need (numpy stack, zarr, h5py, pyarrow, pydantic, useq,
     pymmcore-plus, tifffile, scikit-image, opencv-python-headless);
   - `[gui]`: napari, PySide6;
   - `[cellpose]`: as now;
   - `[scope]`: `gui` + anything only a microscope PC needs. The
     documented install on a microscope becomes `pip install
     "pyclm[scope]"`.
   - Drop `notebook` (move to `analysis`), `pandas-stubs` (to `dev`),
     and `toml` (use `tomllib`).
   `pyclm gui` and `run --gui` print the install line when napari is
   missing.
4. **An install line for interface-71 scopes.** Add an extra `mm71 =
   ["pymmcore==11.2.1.71.0", "pymmcore-plus==0.14.0"]`, so a pip user
   whose adapters are old types `pip install "pyclm[scope,mm71]"`
   instead of discovering the pin. `pyclm check` already prints the
   interface; make its mismatch message name the extra.
5. **Remove the `gui` and `convert_hdf5s` console scripts** (a major
   version is the time).
6. **Custom methods from the command line.** Two mechanisms:
   - a `methods` key in `pyclm_config.toml` or the experiment directory
     (`methods = ["my_patterns.py"]` or `["mylab.patterns"]`): PyCLM
     imports it and registers every `PatternMethod` /
     `SegmentationMethod` / `TrackingMethod` subclass by its `name`;
   - an entry-point group `pyclm.methods` so a lab package that is
     `pip install`ed registers itself.
   This is a code change, not packaging, but it is the largest
   accessibility gain; the `pyclm-write-pattern-method` skill currently
   has to route around it.
7. **A demo for the dry run.** `pyclm new <dir> --demo` writes a
   directory with a small synthetic position list and TIFs (a few
   hundred kB generated by code, so nothing to host), so `pyclm new
   --demo d && pyclm run d --dry --gui` works on any laptop in a
   minute. Real example data, if wanted, goes on Zenodo and is fetched
   on demand.
8. **CellposeSAM on pip.** `tool.uv.sources` only affects uv; pip users
   on Windows get CPU torch. Document
   `pip install "pyclm[cellpose]" --extra-index-url https://download.pytorch.org/whl/cu128`.
9. **Citable releases.** `CITATION.cff` in the repo, the Zenodo–GitHub
   integration for a DOI per release, and the paper reference in the
   README once there is one.
10. **The README as a front door.** Install with pip; a three-command
    dry-run quickstart; the link to the first-time setup guide; the
    image path (currently a Windows backslash path, broken on GitHub).

## 3. Agent skills for newcomers

Drafts in `skills/` (Claude Code `SKILL.md` format: a name and a
trigger description, then the procedure):

| Skill | For | Ends with |
|---|---|---|
| `pyclm-design-experiment` | "I want to light X when Y" | a directory that passes `check`, a preview the researcher has seen, a dry run |
| `pyclm-write-pattern-method` | a rule no built-in method covers | a tested `PatternMethod`, previewed and dry-run |
| `pyclm-microscope-bringup` | a new scope, or hardware failures | config + calibrations checked, first light, wet tests 01–03 |

What they encode that the documentation does not: the order to work
in, the checks that must pass between steps, what not to guess (method
arguments, the affine, the meaning of PFS status strings), and ending
by stating what was not verified.

**Shipping them.** Make the repository a Claude Code plugin marketplace
(`.claude-plugin/marketplace.json` listing one plugin whose `skills/`
are these), so a researcher runs `/plugin marketplace add
Harrison-Oatman/PyCLM` once, with no clone. The skills cite files by
repository path; for pip users, the documentation links should point at
readthedocs instead. Settle this before publishing them.

**Keeping them true.** They name commands, keys and methods. The
release checklist (§4.4) includes "skills still match", and a test can
assert that every `method = ...` and CLI flag the skills mention exists
(cheap: grep the skills, compare against `known_models` and the argparse
parser).

## 4. The development cycle from here

The team is at most two researchers and an agent, with one microscope
that is also used for experiments. The cycle has to keep the scope
trustworthy without a review department.

### 4.1 Branches and versions

- `main` is always releasable and is what the scope runs. The scope
  checks out a **tag**, never a branch.
- Work happens on short branches (`fix/pfs-restart`, `feat/methods-key`)
  merged by pull request, even with one author. The PR is where CI runs
  and where the other researcher (or a fresh agent session) reviews.
- Semantic versions: patch = fixes, no file-format or TOML change; minor
  = new methods, keys, commands, still reading old files; major =
  anything an existing experiment directory or `.zarr` reader would
  notice. `format_version` in the TOMLs and the storage format number
  move only with a major.
- The refactor's stage branches (`Stage0-hygiene`, `STage2-storage`, …,
  29 branches in total) should be deleted once `core-refactor` is merged,
  keeping tags at the useful points.

### 4.2 Every change

1. **Say what and why first.** For anything beyond a fix: a short design
   note in `docs/` (as the stage notes are), reviewed by a human before
   code. The agent writes it; a researcher approves it.
2. **Tests with the change.** A bug from the scope gets a test that
   reproduces it on the virtual microscope where at all possible (the
   PFS-restart and zarr sharing-violation tests are the model); a new
   method gets a unit test and a dry-run test.
3. **Records.** A `CHANGELOG.md` entry under "Unreleased"; a numbered
   `docs/known-issues.md` entry for anything found on the scope; user
   docs in `documentation/` updated in the same PR when behaviour
   changes.
4. **CI green** (§4.5) before merge.
5. **Wet-test the part that touches hardware.** Name the wet-test item,
   or the one-off steps, in the PR. Hardware-only paths are where
   regressions slipped through in this cycle (known issues #32, #34).

### 4.3 Working with the agent

- Keep `CLAUDE.md` current: it is the agent's map. Update it in the PR
  that changes the architecture.
- The agent never pushes, tags, or publishes. The researcher merges,
  tags, and releases.
- Give the agent the evidence: tracebacks, `log.log`, `status.json`, the
  output of `pyclm check`. Ask it to reproduce in a test before fixing.
- Use a fresh session (or `/code-review`) to review an agent's PR; the
  session that wrote the change is the worst reviewer of it.
- For larger work, one stage at a time, as in this refactor: design
  note → approval → implementation → dry testing guide → scope test →
  commit.

### 4.4 Releasing

1. Freeze: merge what is going in; open a `release/x.y.z` PR that bumps
   `version`, moves "Unreleased" in the changelog under the version, and
   updates the README if needed.
2. **Wet tests** on the release candidate: `tests/wet_tests/`, all items
   for a major, items touching changed areas for a minor (the
   changelog says which), none for a pure-software patch. Record
   results in the PR, as `docs/release-wet-tests.md` asks.
3. Docs build clean (`-W`); skills still match (§3);
   `python scripts/check_release.py vX.Y.Z` passes (the changelog section
   dated, the version bumped).
4. Merge, tag `vX.Y.Z` on `main`, publish the GitHub release. The
   publish workflow reruns the release check and the tests, then builds
   and uploads to PyPI (Zenodo mints the DOI once connected).
5. Update the scope to the tag. Each run records `pyclm_version` in the
   store's attributes and the plan metadata.
6. Patch releases for scope bugs come off `main` the same way, minus
   step 2's full run.

Expected rhythm: patch releases whenever the scope finds something;
a minor every few months; a major only with a format change, with a
migration note.

### 4.5 CI to add

- `windows-latest` in the test matrix (the scope's OS; the zarr sharing
  violation was Windows-only).
- A **latest-dependencies job**: build the wheel, install it with pip
  into a clean venv on Python 3.11–3.13 without the lock, and run the
  suite. This tests what PyPI users get and catches upstream breaks
  (pymmcore-plus, zarr, napari) before a researcher does.
- A docs build with `-W`.
- A version check on tags (§2.2).
- Optional: a weekly scheduled run of the latest-dependencies job.

## 5. Decisions (2026-10-01) and status

- **Version 1.1.0**, not 2.0.0. Under that numbering the TOML and storage
  changes of this release are carried by `format_version` and the
  storage format number rather than the package's major version.
- **Name `closed-loop-microscopy`** on PyPI (`pyclm` is refused as too
  close to existing names); the import name and the command stay
  `pyclm`. `[tool.uv.build-backend] module-name = "pyclm"`.
- **Done:** §2.1 metadata and publish URL (the trusted publisher on PyPI
  is still to be configured), §2.3 the `gui` extra and the trimmed core,
  §2.6 the `methods` key and `pyclm.methods` entry points, §2.10 the
  README; `pyclm.__version__` is recorded in the stores; a headless wheel
  install was checked to dry-run on pymmcore 12.5 / pymmcore-plus 0.18.1.
- **Skills** are published separately, in a repository of agent
  resources; the drafts moved out of this repository
  (`C:\FeedbackControl\pyclm-agent-resources\skills`).
- **Done since:** §2.2 the release check (`scripts/check_release.py`, run
  by the publish workflow with the tests), §2.7 `pyclm new --demo`.
- **Open:** §2.4 an `mm71` extra (documented as an explicit pin
  instead), §2.5 removing the `gui` / `convert_hdf5s` scripts (kept for
  1.x), §2.9 `CITATION.cff` and Zenodo, §4.5 Windows and
  latest-dependency CI, known issue #35 (dry-run `binning`).
